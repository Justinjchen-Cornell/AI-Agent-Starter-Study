# 第 2 课：prompt/prompts.yml —— 不写一行代码，用"文字"指挥 AI

> **本节目标**：看懂系统提示词怎么写、如何用文字约束 Agent 行为
> **预计时长**：25 分钟 ｜ **前置**：完成第 1 课，最好已启动过项目

## 先建立直觉：一份"岗位说明书"

上一课我们造好了"大脑"（`model`）。但一个光秃秃的大脑，就像一个**刚入职、什么背景都不知道的聪明新人**——你得给他一份"岗位说明书"，他才知道自己是谁、能干什么、不能干什么。

这份岗位说明书就是 **System Prompt（系统提示词）**。本项目把全部提示词集中放在 `prompt/prompts.yml` 里，而不是散落在代码中——这本身就是一个重要的工程习惯：**改提示词不用动代码**。

（还记得启动服务器时刷出来的那两大段"字典"吗？就是这个文件的全部内容——今天去它的老家看看。）

## ① 先认识 YAML 格式

```yaml
main_agent:                  # 大标题
  system_prompt: |           # 缩进两格 = 属于 main_agent 名下
    你是一个空调公司的智能团队负责人……
```

- `.yml` = 一种**配置文件格式**：纯文本、靠**缩进**分层次、竖线符号表示"下面是一大段多行文字"
- 为什么不用 Python 写提示词？因为这样**改提示词不用懂代码**——产品、运营、你都能改；改完重启即生效

## ② 文件的整体结构 + 三个字段的分工

文件分两大块：

```yaml
main_agent:        # 主智能体（团队负责人）的岗位说明书
  system_prompt: |
    你是一个空调公司的智能团队负责人...

sub_agents:        # 三个子智能体（专员）的岗位说明书
  tavily:
    name: "网络搜索助手"
    description: ...
    system_prompt: ...
  db: ...
  ragflow: ...
```

每个子智能体有三个字段，**先记住它们分别"给谁看"**（下一课写子智能体时直接要用）：

| 字段 | 给谁看 | 作用 |
|---|---|---|
| `name` | 主智能体 | 点名时用："派给**网络搜索助手**" |
| `description` | 主智能体 | **调度依据**——主智能体靠读这段判断"这个任务该派给谁" |
| `system_prompt` | 子智能体自己 | 子智能体干活时遵守的规矩 |

⚠️ 一个关键细节：主智能体 prompt 里提到的助手名字，**必须和子智能体的 `name` 字段一字不差**——因为派活是按名字"点将"，对不上就调度失败。

## ③ 精读主智能体：一份"能约束住 Agent"的提示词五要素

这份提示词是全套课的精华，展示了"能约束住 Agent"的提示词应该包含的 5 个要素：

### 要素 1：角色 + 团队名册（开头）

```
你是一个空调公司的智能团队负责人，负责协调三个专家助手完成复杂任务
你的团队成员如下：
  1. **网络搜索助手**  2. **数据库查询助手**  3. **RAGFlow助手**
```

先给身份（"团队负责人"），再给名册。给大模型戴上"**角色帽子**"——模型本身是"什么都聊的通才"，这段话让它入戏成有职责、有手下、有目标的负责人。

### 要素 2：决策规则——什么情况找谁

```
- 对于背景知识和外部知识 → 网络搜索助手
- 对于企业内部专有知识 → RAGFlow助手
- 对于商品数据       → 数据库查询助手
- 如果边界并不明确，则全部使用
```

给 AI 一张"**决策地图**"。注意最后一句"边界不明确则全部使用"——这是一种**兜底策略**：宁可多查，不可漏查。写提示词时，**替 Agent 想清楚它可能犹豫的场景，提前给出答案**。

### 要素 3：硬性约束——文件只能写在工作目录

```
- 强制要求：你必须且只能在该工作目录下进行所有文件的创建、读取和保存操作。
```

没有这句，Agent 可能把文件写到系统任意位置——安全问题。提示词是 Agent 的**第一道安全防线**（第 9 课的 `path_utils.py` 是第二道代码防线，双保险）。

### 要素 4：防"偷懒"和"幻觉"的执行顺序（全文最精彩）

```
【关键执行顺序】
1. 必须先调用子智能体获取信息。
2. **绝不允许**在获取信息之前调用文件生成工具。
3. 严禁使用 "等待子任务完成" 之类的占位符内容生成文件。
4. 先搜索再生成，要分两步进行：不要在一步（同一个 Tool Call 列表）中同时做这两件事。
```

为什么需要这段？因为 LLM 有个天性：**急于交差**。不写死顺序，它经常不搜索就直接编一份报告（幻觉），或者生成一份写着"等待搜索结果"的占位符文档糊弄你。

> 🧠 **这是提示词工程的实战精髓**：不是描述"你希望它怎样"，而是**预判它可能会怎么把事情搞砸，然后把每条歪路都堵死**。这几条显然是作者踩过坑后补上的——你以后调试自己的 Agent 时，也会经历"出 bug → 在提示词里加一条禁令"的循环。

### 要素 5：输出标准——可量化

```
内容要求丰富且全面，不少于1000字
无论任务复杂程度，都需要生成一个todo-list进行规划
```

给**可量化的标准**（1000 字、todo-list），而不是"写得详细点"这种模糊要求。

## ④ 精读子智能体：小而专

对比看子智能体的提示词（网络搜索助手）：

```
……至少检索3个角度的该问题，一共最多进行5次检索，如果超过5次，则不允许继续检索
```

**范围窄、规则具体**。"至少 3 个角度"保证搜索广度；"**最多 5 次**"防止无限调用烧钱烧时间——这种"**上下限**"写法非常值得学。

RAGFlow 助手里还有一句：

```
保留检索的全部信息，不需要进行概括性总结，你需要将检索到的原始信息传输给后续
```

为什么不让子智能体总结？因为**每多一层总结就多一层信息损失**。子智能体是"**搬运工**"，主智能体才是"**撰稿人**"——分工明确。

## ⑤ 一个生活化的类比：这套体系是一家餐厅

- **主智能体的 prompt** = 店长手册：会接待顾客（用户请求）、知道后厨有谁（三个助手）、什么单派给谁（决策规则）、上菜前必须确认食材真的到了（关键执行顺序）
- **子智能体的 prompt** = 各档口师傅的操作规范：只管自己的一道工序，做完**原样交回**，不许擅自摆盘

## 🤫 彩蛋：提示词也会"写飘"

仔细读会发现提示词里有处小矛盾——文中提到"文件生成助手"，但团队名册里只有三个助手、并没有它。**现实世界的提示词也会写得前后不一致**，这正是提示词工程是一门手艺的原因。也许你会是第一个修复它的人。

## 📌 概念卡

| 概念 | 一句话 |
|------|--------|
| system_prompt | AI 的"岗位说明书"：是谁、听谁、不许干嘛 |
| YAML | 不写代码就能改的配置：缩进分层，竖线写大段文字 |
| 三字段分工 | name / description 给主智能体调度用；system_prompt 给自己遵守 |
| 硬约束 + 兜底 | "必须/绝不 + 数字上下限"堵死歪路；模糊场景提前给答案 |
| 配置与代码分离 | 改人设不改代码——本项目最妙的设计之一 |

## ✍️ 复述题（先自己想，再展开对照）

1. 用"员工手册"的比喻说说：system_prompt 到底在干什么？
2. 子智能体的三个字段（name / description / system_prompt）分别"给谁看"？
3. 如果把"边界并不明确，则全部使用"这句删掉，Agent 遇到模糊任务可能怎样？
4. "最多进行 5 次检索"这种硬数字是干嘛的？不加会发生什么？
5. 假设要给系统加一个"天气查询助手"，主智能体的 prompt 里需要同步改什么？

<details>
<summary>💡 参考答案（用自己的话答对意思即可）</summary>

1. 就像给刚入职的聪明新人发一本员工手册：先定岗位（角色），再讲工作流程（什么单派给谁），最后划红线（绝对不许做什么）。它不改变模型的能力，而是改变它的"身份感"和"行为习惯"。
2. `name` 和 `description` 都是**给主智能体看的**——主智能体靠它们"点将"和判断"该派给谁"；`system_prompt` 是**给子智能体自己看的**——它干活时遵守的规矩。
3. Agent 遇到"既像外部知识又像内部数据"的模糊任务时可能犹豫、漏查，甚至随便挑一个助手导致结果不完整。那句兜底 = 明确告诉它"拿不准就都查一遍"。
4. 给 AI 定 KPI（至少 3 个角度，保证质量）和预算上限（最多 5 次，防它无限搜索烧钱烧时间）。不加下限会偷懒，不加上限可能失控。
5. 三处：① 把"天气查询助手"加进团队名册（名字和它的 `name` 字段一字不差）；② 在决策规则里加一条"当用户问天气时 → 天气查询助手"；③ 新助手自己的规矩（比如查询范围）写在它自己的 `system_prompt` 里。

</details>

## 🎁 动手实验（2 分钟）

1. 打开 `prompt/prompts.yml`，把开头的"**空调公司**"改成你喜欢的场景（比如你的公司/项目名）
2. 保存 → 重启服务器（顺便留意窗口里刷出来的第一段字典）
3. 观察：打印出来的 `system_prompt` 里公司名已经变了——**改一行文字，AI 的"身份"立即更新**
4. 玩够了改回来，或留着看它干活时怎么自称
